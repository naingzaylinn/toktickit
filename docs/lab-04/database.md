# Issue #57 database implementation and recovery

Database foundation only, on `feature/sprint4-actions-database`. The approved
[Section 9 contract](specification.md#9-proposed-database-and-migration-design)
is implemented without changing the eight Ticket statuses or existing APIs.

## Storage and enforcement boundary

`ActionTaken` stores a UUID generated by Prisma, parent Ticket, original
performer, required independent assignee, separate three-value `ActionStatus`,
required `actionDescription`/`actionResult`, follow-up flag (default false),
nullable follow-up/attachment notes, required client request key, version
(default 1), creation time (database now) and Prisma-managed update time.
IDs/FKs remain PostgreSQL TEXT, matching existing UUID-string models; raw SQL
must supply UUID IDs and updatedAt. No duplicate action date column is added.

`ActionTakenRevision` stores a UUID, Action FK, editor FK, required version,
all five editable content fields, assignee/status snapshots and creation time.
User inverse relations distinguish performer, current assignee, revision editor
and historical assignee. Ticket adds `actionsTaken` and workflowVersion default 0.

Database constraints enforce required columns, enum membership, six restrictive
FKs, unique `(ticketId, performedById, clientRequestId)` and unique
`(actionId, version)`. The exact contract indexes support ordered ticket history,
performer history, assignee lookup, ticket/status counts and revision editor/
assignee lookup. The two proposed Ticket composites support status/owner counts
and recent-ticket ordering without duplicating existing owner/requester indexes.
The recent index explicitly uses `updatedAt DESC, ticketNumber ASC`, matching
the existing Queue query and BR-16. An isolated forced-candidate EXPLAIN test
checks that this index supplies ordering without a Sort node. It does not prove
natural planner preference or measured speed on the tiny fixture. Large-dataset
query plans and latency measurements remain later performance work.

`SeedUserIdentity` is additional local seed metadata, introduced to address the
reviewed mutable-email identity defect. Its immutable seedKey maps uniquely to
a User FK with restrictive deletion. It is not an Action business field or API.

The two main design decisions are separate child records that leave primary
Ticket ownership independent, and full revisions alongside an editable current
projection that retain previous evidence. Versions support later stale/ABA
checks; createdAt is the single original action date.

**The database does not enforce append-only revisions or performer/date
immutability.** A privileged SQL writer can update/delete revisions or change
the projection. Issues #58/#60 must provide authenticated actor attribution,
immutable original fields, revision 1 with editor=performer, contiguous versions,
one full revision per real mutation, normalized idempotent replay comparison
against revision 1, no-op detection and transaction rollback guarantees.
They must enforce trimmed text/lengths/conditional notes, eligible assignees,
three-state transitions/cancellation reasons/terminal restrictions, session and
role/ownership authorization, optimistic concurrency, ordered Ticket/Action/User
locking, parent activity/version increments and the resolution gate.
No endpoints, services, React/UI, dashboard or workflow logic were added here.

## Migration safety and operational recovery

`20261011000000_actions_taken/migration.sql` was generated from the old and new
local Prisma schemas, inspected, and wrapped in PostgreSQL BEGIN/COMMIT. It adds
an enum, two empty Action tables, an empty seed identity table, indexes/FKs and Ticket.workflowVersion with NOT NULL
default 0. It contains no legacy-row UPDATE, table/column DROP, DELETE, TRUNCATE,
rename or TicketStatus modification. Existing resolved/closed tickets may have
zero actions. No historical work is fabricated. The transaction ensures a failed
statement rolls back this migration's DDL; Prisma records its failure separately.

Before a later real deployment, capture a verified backup plus counts/IDs/full
snapshots of existing tables and confirm the target URL/schema. Deploy through
Prisma migrate deploy after review; this task deploys only to generated test
schemas. Adding a column and building indexes takes locks on Ticket: deployment
on a large/live database needs an appropriate maintenance window. Lock duration
on production-scale data has not been measured.

If deployment fails:

1. Stop dependent application rollout. Inspect Prisma migration status/logs and
   database catalogs; distinguish a fully rolled-back attempt from manual or
   partially applied changes. Preserve all existing action and revision rows.
2. For this transactionally rolled-back migration, verify the new objects and
   column are absent and baseline data intact. Only then use
   `prisma migrate resolve --rolled-back 20261011000000_actions_taken` followed
   by `prisma migrate deploy` after fixing the cause. Never mark it applied
   without verifying every expected object. Do not edit a migration already
   successfully deployed elsewhere; use a new corrective migration.
3. If the migration succeeded and real work was recorded, prefer a new additive
   forward repair. Reverting application code leaves the added tables/data in
   place. Do not drop ActionTaken/ActionTakenRevision or reset the database.
4. If a destructive recovery becomes unavoidable, obtain separate approval,
   export all new work, restore a verified backup in another environment and
   reconcile post-backup records before any cutover.

The recovery test runs actual Prisma deploy/resolve commands against a populated
generated schema, injects a failure before COMMIT, verifies full rollback and
blocked unresolved retry, then resolves/redeploys. It also records an action and
revision, proves deployment retry preserves them and repairs a deliberately
incorrect default via a separate forward migration without changing either row.
The injected failure must complete without timeout/spawn error; its ledger row
must exist and be unfinished/unresolved. Prisma 5.22 on this setup reports an
aborted-transaction error while recording the explicit-transaction failure,
and may leave logs null; the test also accepts Prisma's normal P3018 diagnostic.
The retry must complete and report P3009 naming that migration, with its full
selected ledger snapshot unchanged. Merely returning nonzero is insufficient.

## Demonstration seeds and test isolation

Existing Lab 1–3 fixtures remain. Full seeding adds eight stable Lab 4 tickets,
one per Ticket status, with all priorities, assigned/unassigned ownership and
zero/one/multiple actions. It adds pending/completed/cancelled actions, completed
work with/without follow-up, optional-note variations, distinct owner/performer/
assignee identities, two full revisions per action and historical inactive
assignment. Historical inactive assignment represents a worker who was eligible
when assigned and later deactivated; seeds materialize audit snapshots, not API
operations. Resolved/closed examples satisfy the gate. An additional active empty requester
and staff-with-no-performed-actions provide zero metric populations while other
users/tickets provide nonzero ones.

Stable UUIDs identify Lab 4 intents, and unique request keys identify existing
Lab 3 intents. A ticket and its action/revision examples are created together
only if the intent is absent. Reruns skip the entire existing aggregate: they
never repair missing history, reset versions/status/ownership/assignment/content,
or replace passwords. Existing reference data and development-requester changes
are also preserved with `upsert update: {}`. If demo users are later ineligible,
new Lab 4 work is skipped rather than resetting their role/activation. Production
mode rejects the seed before writes. Seeds remain explicitly local demo tools,
not migrations or a means to modify production data.

User identity adoption is atomic. Existing requesters retain actual persisted
DevelopmentRequester IDs, even when those differ from the default UUIDs. Legacy
staff/Admin accounts are adopted by their original emails once, retaining their
random UUIDs and all fields; new installations use deterministic staff UUIDs.
Thereafter all requester/staff/Admin lookups use the durable seedKey→User ID
mapping. The Lab 4 empty requester is always matched by its fixed UUID.
Changing email, name, credentials, role or activation does not recreate accounts.
Additional persisted Lab 2 requesters retain the previous user-copy behavior.

If a legacy random-ID account was renamed before mappings exist, its identity
cannot be inferred safely. Missing seed identities in the presence of unknown
legacy users fail closed, rolling back user/requester/mapping adoption instead
of issuing replacement credentials. An operator must verify the existing User
ID and register the appropriate SeedUserIdentity key before reseeding; do not
guess from name/role or reset email. Reference upserts run before this adoption
transaction, so first-time reference records can still be created on a failed
seed; existing reference fields are never overwritten. This conservative guard
can also require explicit registration in partially seeded databases with unrelated
users. No mappings were registered in the developer database during this task.

The `{ lab4: false }` seed option retains the original exact Lab 3 fixture
distribution for its unchanged assertions and the Lab 2 reference-data test.
Full-seed coverage is in the new isolated Lab 4 test. The runner removes demo
action/revision children only inside its own generated schema before legacy
ticket-deletion fixtures; FK enforcement stays enabled. Fixture migration helpers
own their transaction and omit deployment BEGIN/COMMIT wrappers when splitting
ordinary SQL statements. No developer records are deleted or seeded.
